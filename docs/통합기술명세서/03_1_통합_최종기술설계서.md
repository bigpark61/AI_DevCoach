## v3.0 Neon 운영 DB 교차검증 요약 (2026-11-19)

**Neon 앱 연결은 확인되었지만 실제 카탈로그 SQL 조회는 실패했습니다.** 프로젝트 검색 도구가 `Tool not found`, 테이블 조회 도구가 `project_id` 식별 오류를 반환하여 이 세션에서는 운영 DB의 모든 컬럼·PK·FK·인덱스를 확정할 수 없었습니다. **운영 DB에 데이터를 쓰거나 스키마를 변경하지 않았습니다.**

- **직접 관찰한 운영 화면:** `AI_DevCoach` / `production` / `neondb` / `public`; 화면에 보이는 `alembic_version`, `users`, `profiles`, `assessments`, `plans`, `task_progress`, `task_submissions`, `github_analysis_runs` 등 테이블명.
- **AI 대화 데이터:** 선택된 테이블에 `id bigserial`, `user_id text`, `role text`, `content text` 열과 user/assistant 역할의 기록 4행이 보이며 코드의 `agent_chat_messages`와 호환되는 모습이나 **테이블명이 스크린샷에서 명확히 보이지 않으므로 식별 확정은 보류**.
- **운영 검증 대기:** 전체 테이블 수, 물리 칼럼 정의, PK/FK, 인덱스, Alembic revision 값, 실제 API DB 연결 상태.
- [운영 데이터 모델 및 근거별 ERD](03_3_ERD_물리스키마_소스확인.md) · [읽기 전용 검증 SQL](03_5_Neon_운영스키마_검증SQL.md)

## 4. 핵심 AI 활용 상세

### 4.1 AI Agent (실제 구현)

`backend/agent.py`의 `TOOL_DEFINITIONS`는 `search_learning_resources`, `get_my_learning_progress`, `list_my_tasks` 세 도구를 정의합니다. `backend/main.py`의 `agent_chat()`이 로그인 사용자의 도구 핸들러를 구성하여 `run_learning_agent()`에 전달합니다. 도구는 조회 전용이며 학습계획·진도 직접 변경은 허용하지 않습니다.

### 4.2 RAG 파이프라인 (실제 구현)

`backend/knowledge.py`의 `_load_chunks()`는 `backend/knowledge/*.md` 파일을 `##` 제목 기준으로 분할하여 `source_id`를 부여합니다. `search_knowledge()`는 토큰화와 BM25 계열 어휘 점수로 검색하며, `agent_chat()`은 검색 출처를 추적하여 답변의 미확인 출처를 제거합니다. **벡터 임베딩/벡터 DB 기반 RAG는 아닙니다.**

### 4.3 Long-term Memory (구현 범위 정확히 구분)

`agent_chat_messages` 테이블에 사용자별 메시지와 출처 ID를 영속 저장합니다. `agent_chat()`은 최근 8개 메시지를 DB에서 조회해 대화 맥락에 사용합니다. `profiles`, `assessments`, `plans`, `task_progress`, `learning_activity_logs` 등에도 개인화 학습 이력이 지속 저장됩니다. 다만 **장기 기억 요약·의미 검색·자율 재계획은 구현 확인되지 않았으므로 별도 고도화 과제**입니다.

### 4.4 GitHub 프로젝트 분석 (실제 구현 확인)

이전 초안의 '미구현 가능성' 판정을 수정합니다. `analyze_github_project()`가 GitHub REST API로 저장소/브랜치/Commit/트리/README/언어/최근 커밋을 수집하고, `_readme_score()`, `_detect_tech_stack()`, `_project_review()` 등을 활용합니다. `GitHubProjectReview` Pydantic 스키마와 `github_analysis_runs` 저장 테이블이 존재합니다. 공개 저장소만 지원합니다. **운영에서 실제 분석 성공 여부는 별도 확인**해야 합니다.

## 5. ERD 및 운영 물리 모델

[Neon 운영 화면과 개발 SQLite 스키마를 구분한 ERD](03_3_ERD_물리스키마_소스확인.md)를 참조합니다. `plans.data`, `assessments.answers/result`의 JSON 텍스트 저장 구조는 **개발 SQLite 코드 확인 결과**이며 PostgreSQL의 실제 컬럼 타입이 같다는 뜻은 아닙니다. PK·FK 실물 확인 전까지 ERD 선은 **논리적 관계**를 의미합니다. `alembic_version` 테이블은 운영 화면에서 확인했으나 revision 값은 아직 조회하지 않았습니다.

## 6. API 명세

[실제 API 경로/함수 매핑 및 요청 모델](03_2_API_명세서_소스확인.md)을 참조합니다. 최종 전체 경로 확정은 FastAPI의 `/openapi.json` 자동 추출과 비교해야 합니다.

## 7. 화면 설계

`frontend/index.html`은 `#main` 영역을 제공하고 `frontend/app.js`가 화면을 동적으로 렌더링하는 단일 페이지 구조입니다. `renderAuth()`, `renderPasswordResetRequest()`, `renderPasswordReset()`, `renderProfile()`, `continueUser()`, `continueLearnerView()`, `renderDashboard()`, `openAdminView()`를 확인했습니다. 프론트엔드는 `fetch` 기반 공통 `api()` 함수로 서버를 호출합니다.

## 8. 보안 및 운영

- PBKDF2 기반 비밀번호 해싱, HttpOnly/SameSite=Lax 세션 쿠키, `COOKIE_SECURE=true`(HTTPS 운영).
- 비밀번호 재설정 토큰은 해시로 저장하며 30분 만료·1회 사용.
- 관리자 접근은 `ADMIN_EMAILS` 허용 목록으로 통제.
- GitHub 분석 URL은 HTTPS github.com 저장소로 제한하며 공개 저장소만 지원; 외부 응답 및 민감정보 처리 주의.
- `.env`와 API 키는 Git에 업로드하지 않음. PostgreSQL은 Alembic 마이그레이션 후 배포.

## 9. 테스트 현황과 한계

- 소스 확인: `tests/test_app.py`는 `unittest`, `TestClient`, 임시 SQLite DB, Mock/patch를 사용합니다. 인증·권한, RAG 출처, Agent, 학습계획, GitHub 분석 등 테스트 케이스가 존재합니다.
