### 1.1 추진 배경

AI·SW 학습자는 자신의 수준을 객관적으로 판단하기 어렵고, 적정 난이도의 계획을 세우거나 실제 GitHub 코드에 근거한 피드백을 받기 어렵다. 학습 일정과 코드 개선 활동이 분리되어 계획을 지속적으로 보정하기도 어렵다. AI DevCoach는 **진단 → 계획 → 실행 → GitHub 증거 분석 → 코칭의 순환 구조를 목표로 한다.

### 1.2 프로젝트 차별화

단순 질문응답 챗봇이 아니라 학습자의 승인된 주차별 과제와 GitHub 코드·README·Commit을 연결해 개선 근거를 제시하고, 다음 학습 행동으로 환류한다. AI 판단은 사실로 확인된 코드 증거와 추정 의견을 분리하고, 자동 완료 판정 대신 검증 절차를 둔다.

## 2. 목표 및 성공 기준

1. 사용자가 가입·로그인하여 프로필과 수준진단을 수행한다.
2. 진단 결과와 학습 가능 시간에 따른 학습계획을 수립하고 사용자가 수정·승인한다.
3. 승인된 계획을 주차별 과제로 관리하고 진도를 시각화한다.
4. 공개 GitHub 저장소의 실제 파일·README·Commit을 수집하고 분석 근거를 제공한다.
5. 코드 리뷰·학습 코칭·계획 재조정을 연계한다.
6. 외부 접속 가능한 웹서비스를 제공하고 실제 학습자 5명 이상으로 사용성을 검증한다.

## 4. 사용자 화면 구성 및 이동 체계

### 4.1 화면 계층

```text
사용자
├─ 회원가입 → 로그인
├─ 로그인
│  ├─ 최초/미완료: 학습자 프로필 설정
│  │  └─ 수준진단(프로필 확인 → 진단 시작)
│  └─ 기존/완료: 대시보드
└─ 비밀번호 찾기(재설정) → 로그인

수준진단
├─ 진단 진행 → 진단결과
└─ 진단결과 → 학습계획 수립
   └─ 조건 저장 → 계획 생성/수정 저장 → 계획 승인 → 대시보드

대시보드(메인)
├─ 나의 학습현황
├─ 주차별 계획 → 과제관리(주차별 학습관리)
├─ 학습코칭 → 계획 재조정 → 진도대시보드로 돌아가기
├─ 진도분석 보기
└─ GitHub 분석
   ├─ 저장소 분석 요청
   └─ 분석 이력
```

### 4.2 화면 목록(화면 ID는 기존 상세설계와 정합성 유지)

| 구역 | 화면 ID | 화면명 | 주요 이동 |
|---|---|---|---|
| 사용자 | UI-01 | 회원가입 | 로그인 |
| 사용자 | UI-02 | 로그인 | 프로필 또는 대시보드 |
| 사용자 | UI-02A | 비밀번호 재설정 | 로그인 |
| 사용자 | UI-03 | 학습자 프로필 등록 | 수준진단 |
| 사용자 | UI-04 | 프로필 수정 | 수준진단/대시보드 |
| 수준진단 | UI-05~09 | 진단 시작·응답·제출·결과·추천 | 학습계획 |
| 학습계획 | UI-10~14 | 조건·생성·미리보기·수정/승인·확정 | 대시보드 |
| 진도/과제 | UI-15~20 | 진도 대시보드·주차·과제·통계·코칭·재계획 요청 | 대시보드 |
| GitHub | UI-21~28 | 저장소 등록·분석·구조·README·Commit·AI 진단·과제 검증·이력 | 대시보드/과제 |

**화면 전환 규칙**: 로그인 직후 사용자별 프로필·진단·승인 계획 상태를 확인하여 다음 미완료 단계 또는 대시보드로 이동한다. 계획 수정과 재조정은 기존 승인 계획을 자동 덮어쓰지 않고 사용자 확인 후 확정한다.

## 5. 핵심 업무 흐름

### 5.1 신규 학습자

회원가입 → 로그인 → 학습자 프로필 → 수준진단(20객관식·2서술형) → 결과 확인 → 학습계획 조건 입력 → 초안 생성 → 수정·저장 → 승인 → 대시보드.

### 5.2 반복 학습

대시보드 → 주차별 과제 수행·시간 기록 → GitHub 저장소 등록·분석 → 결과 및 개선 과제 확인 → AI 학습코칭 → 계획 재조정 요청 → 사용자 승인 → 갱신된 주차별 계획.

### 5.3 GitHub 분석 상세 흐름(목표 설계)

저장소 URL 등록 → 접근·소유권/권한 검증 → GitHub REST API로 README·파일 트리·Commit 조회 → 중요 파일 선별 및 비밀정보 제거 → 정량·규칙 분석 → OpenAI 기반 정성 분석 → 증거 경로·Commit SHA 검증 → PostgreSQL에 결과/이력 저장 → 학습과제 완료 기준과 비교.

## 7. PostgreSQL 데이터 설계

| 데이터 영역 | 주요 테이블(목표 논리 모델) | 관계 |
|---|---|---|
| 계정/프로필 | `users`, `learner_profiles`, `user_consents`, `password_reset_tokens` | 사용자 중심 |
| 수준진단 | `assessment_sessions`, `assessment_answers`, `assessment_results` | `user_id` |
| 학습계획 | `learning_plans`, `learning_plan_weeks`, `learning_tasks`, `learning_plan_revisions` | 사용자·승인 계획 |
| 진도관리 | `learning_time_logs`, `task_submissions`, `task_verifications` | `task_id` |
| GitHub 분석 | `github_repositories`, `github_analysis_runs`, `github_analysis_results`, `github_analysis_findings` | `repository_id`, `analysis_id` |
| 코드 리뷰 | `code_reviews`, `code_review_findings` | 분석·파일·Commit SHA |
| AI 코칭 | `coaching_sessions`, `coaching_messages`, `coaching_feedback` | 사용자·과제 |

GitHub 분석 상세 결과는 PostgreSQL `JSONB`로 저장할 수 있으며 Firebase는 필수 구성요소가 아니다. 위 테이블명은 설계 목표이므로 실제 GitHub ORM·마이그레이션과 대조 후 최종 확정한다. 운영 DB와 테스트 DB(또는 Neon Branch)는 분리한다.

## 8. AI Agent 설계

| Agent/서비스             | 입력             | 도구/처리                            | 출력            |
| --------------------- | -------------- | -------------------------------- | ------------- |
| Assessment Scorer     | 서술형 응답·루브릭     | OpenAI API, 객관식 정답 비교            | 점수·역량 피드백     |
| Learning Planner      | 진단·목표·시간       | 현행 규칙 기반 계획 검증, 향후 LLM 계획 제안     | 승인 전 주차별 계획   |
| GitHub Analysis Agent | 저장소·Commit SHA | GitHub API, 파일 구조·README 분석, LLM | 근거 기반 프로젝트 진단 |
| Code Review Agent     | 주요 코드·분석 결과    | 정적 분석, OpenAI API                | 문제·근거·개선안     |
| Coaching Agent        | 진도·과제·진단·분석 결과 | DB 조회 Tool, LLM                  | 다음 학습 행동 제안   |


안전 기준: 저장소의 `.env`·키·개인정보를 LLM에 전달하지 않으며, GitHub 원문은 신뢰할 수 없는 입력으로 처리한다. AI 판단만으로 과제를 자동 완료하거나 사용자 승인 없이 기존 계획을 변경하지 않는다.

### 주요 E2E 테스트

1. 회원가입 → 로그인 → 프로필 → 수준진단 → 진단결과.
2. 조건 저장 → 계획 수정 → 계획 승인 → 대시보드.
3. 주차별 과제 상태·시간 기록 → 진도율 반영.
4. 공개 GitHub URL 입력 → 수집·분석 → 분석 이력 재조회.
5. 분석 결과와 과제 기준 연결 → 코칭 → 재계획 요청 → 사용자 승인.
6. 비밀번호 재설정 링크 만료·재사용 차단, 사용자 간 데이터 접근 차단.
7. `.env` 비노출, OpenAI/GitHub API 실패 및 DB 연결 실패 시 오류 처리.

## 12. 위험 요소 및 대응

| 위험 | 대응 |
|---|---|
| AI가 확인되지 않은 코드 기능을 단정 | 파일 경로·SHA·근거 표시, 사용자 검토 |
| GitHub API 호출 제한 | 파일 크기·개수 제한, 캐시, 호출 오류 처리 |
| API 키 유출 | `.env` Git 제외, 서버 환경변수·Secrets, 로그 마스킹 |
| PostgreSQL 스키마 불일치 | Alembic 마이그레이션, 배포 전 테스트 DB 검증 |
| 장시간 AI 분석 | 분석 상태 DB 기록, Polling, 재시도/실패 처리 |
| 범위 과다 | 공개 Python 저장소 우선, PR 단위 MVP 개발 |
| 테스트 환경이 운영 DB를 변경 | 테스트 DB 또는 Neon Branch 분리 |
| 이메일 발송 설정 미비 | SMTP 구성 검증, 로컬 개발 모드 운영 배포 금지 |
